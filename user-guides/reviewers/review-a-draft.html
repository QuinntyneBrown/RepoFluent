Reviewing a draft

You are the control that stops generated content reaching learners unchecked. RepoFluent's job is to give you everything you need to judge a draft, and to make your decision permanent once you make it.

  • Reviewer
RF-UG-10

What you are actually approving

The button says Approve this checksum, not "approve this curriculum", and the wording is exact. You approve one immutable set of bytes together with one specific validation report. Three things follow from that.

  • If the author changes anything at all, your approval no longer applies and the new bytes need a new decision.
  • An administrator can only publish content that carries a matching approval, so nothing can slip past you between approval and publication.
  • A decision is recorded once and cannot be edited, replaced, or withdrawn.
There is no undo, and no second attempt

Approving or rejecting is final for that version. If you reject a draft you cannot later approve the same bytes — the author must produce a new version. Read the whole panel before you press either button.

Previewing as a learner would see it

Press Preview draft. The draft renders through exactly the same renderer a learner uses — not a separate preview mode — so what you see is what they get. Four safeguards are active, and the preview shows them to you so you can be sure.

Presentation path
Production renderer. There is no risk of approving something that looks different once published.
Learner state
Progress writes disabled. Previewing does not create or disturb any learner record.
Assessment state
Assessment writes disabled.
Answer policy
Protected answers withheld. Correct answers are removed from the response itself, not merely hidden on screen.

A receipt line beneath repeats the package checksum and the issue-set checksum, so the thing you are looking at is provably the thing you are about to approve.

The preview shows one lesson

The learner-equivalent preview renders the first lesson of the first module of the first course. It is a rendering check, not a way to read the entire curriculum. To assess coverage and structure, use the contract model workbench described next.

What you can judge from the preview: whether prose reads correctly, whether diagrams have meaningful captions, whether code references point at plausible symbols and revisions, and whether callouts and examples are useful rather than filler. What you cannot judge from it: whether the whole curriculum is complete.

The contract model workbench

Inspect contract model opens a read-only view of the entire package as RepoFluent understood it, in five numbered sections. This is where the real review happens.

Section Contains Look for
01 Package metadata Stable package identifier, contract and package versions, owner, who created it and when, and for each repository its relative root, commit, documents, and capture time. Does the source snapshot match the code this content claims to describe? Is the commit recent enough to be worth teaching?
02 Architecture model Systems and their subsystems with boundaries, typed relationships from source to target, and terminology definitions. Are the boundaries and dependencies right? A wrong architecture claim teaches a wrong mental model that is hard to unlearn.
03 Learning model Courses in order with audience, difficulty, duration, tags, prerequisites, completion rules, and structure. Is the ordering sensible? Are prerequisites honest? Is the estimated duration plausible?
04 Assessment model Purpose, title, attempt limit, time limit, feedback release, item types, selection, and the mapping of each item to objectives, systems, and subsystems. Does every objective have coverage? Are questions testing capability rather than trivia? Correct answers are withheld from you here by design — a notice says so.
05 Provenance and identity Resolvable citations with their evidence type, plus the author's declared assumptions, omissions, conflicting sources, and unresolved questions, and the canonical formatting rules applied. Read this first, not last. The unresolved questions and assumptions are the agent telling you where it was not sure. That is your shortlist.

A Contract extensions panel is embedded here too, listing any extensions the package declared and confirming that core interpretation is unchanged by them.

Acknowledging warnings

If validation produced warnings, the warning gate in the validation evidence reads Acknowledgement required and an Acknowledge exact warnings button appears. You cannot approve until it is cleared.

  1. Read the issues table first

    Every warning is listed with its code, severity, exact JSON path, and message. Acknowledging without reading defeats the purpose of the gate. Codes are explained on Validation issues.

  2. Press Acknowledge exact warnings
    What you should see The gate changes to Warnings acknowledged, and the change is announced to assistive technology.

The acknowledgement is bound to two checksums: the package bytes and the exact set of issues. It is not a blanket "warnings are fine" setting. If the package is revalidated and the issue set changes, your acknowledgement is invalidated automatically and has to be made again against the new set.

Recording your decision

Rationale

The Review rationale box is hinted Record the evidence checked or explain a rejection, and it is stored permanently alongside your decision and both checksums.

  • For an approval it is optional — but it is what a future auditor will read to understand why this content was trusted. Write what you actually verified.
  • For a rejection it is required. The Reject this checksum button stays disabled until you type something.

Approving

Press Approve this checksum. A Review decision evidence region appears showing an Approved pill, your identity as reviewer, the package and candidate version, the warning-gate binding, the package checksum, the validation-report checksum, and your rationale. The draft is now publishable by an administrator, and by nobody else.

Rejecting

Press Reject this checksum. The same evidence region appears with a Rejected pill and your explanation. The lifecycle records the failure code CLI_REVIEW_REJECTED. The author's next step is a new version, not an edit of this one.

If the button will not work

Symptom Cause
No review buttons at all You are not the Reviewer persona, or the draft is not in a reviewable state — it may already have a decision.
Approve is refused There is an unacknowledged warning, or the validation report changed under you. Reload the page and read the evidence again.
Reject stays disabled The rationale box is empty.
A conflict message about a stale checksum The package or its report is no longer what your page thinks it is. Reload before deciding — this guard exists precisely so you cannot approve something you did not look at.

Also yours: comparing versions

Reviewers, as well as administrators, can compare two published versions of the same package to see what changed and decide whether learners need to redo anything. That is the subject of Comparing versions.

You may review your own upload

In this release nothing stops the same person from authoring and reviewing the same package. That is deliberate so one person can exercise the whole workflow, but it means separation of duties is a matter of your team's practice rather than something the product enforces.
