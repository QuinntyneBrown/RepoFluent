Lifecycle and evidence

A curriculum moves through a fixed sequence of states, and every transition leaves evidence that the next transition is bound to. This page is the map: what each state means, what each evidence panel proves, and which identifier to quote when you need help.

  • All roles
RF-UG-13

The states

The page header shows a strip reading Draft → Validate → Review → Publish → Retire. The underlying states are slightly more precise, and the status pill in panel 02 names the one you are in.

State Pill reads Meaning Next move
Received Queued for validation Your bytes are accepted and have a checksum, but nothing has examined them yet. Wait. A worker picks it up automatically.
Validating Validating A worker is applying the eleven check categories. Wait. If it stays here over five minutes it is stale and can be retried.
ValidationFailed Validation failed At least one blocking error. There is no draft and no way forward from here. The author fixes the package and uploads a new version.
Draft Ready for review Valid content imported, invisible to learners. Warnings may be outstanding. A reviewer previews, acknowledges warnings, and decides.
Approved Approved A reviewer has bound an approval to this exact checksum. An administrator publishes.
Rejected Rejected A reviewer refused these bytes, with a required rationale. Final. A new version. This one is finished.
Published Published One immutable version exists and is active for assignment. Assign it, compare it, or eventually retire it.
Retired Retired Withdrawn from new assignment. Existing assignments still work and the content is still resolvable. Nothing further. History is retained permanently. See Retiring a version.
States only move forward

There is no way back. Nothing is ever un-approved, un-published, or un-rejected. Correction always means a new version, which is what makes a learning record from six months ago still mean something.

The lifecycle operations panel

Labelled Lifecycle operational evidence, this is the fastest way to see where a curriculum has got to and whether it is waiting on somebody. It has four parts.

Active stage and a pill
Action required means a person has to do something next. In control means the system is working and you should wait.
Completed stage chips
Intake, Validation, Draft import, Review, Publication, Retirement. Each lights up as it completes, so you can see progress at a glance.
A six-cell timeline
Intake recorded, Validation started, Validation completed, Review recorded, Publication recorded, Retirement recorded — each with a timestamp or a placeholder.
Support correlation identifier
The value to quote when you report a problem. See Identifiers below.

Reading the placeholders

An empty timeline cell tells you something specific rather than nothing.

Placeholder Means
Awaiting worker Accepted but validation has not begun. If this persists, the background worker is not running.
Not completed Validation started and has not finished.
Not reviewed No review decision exists yet. A reviewer is the blocker.
Not published No publication yet. If the state is Approved, an administrator is the blocker.
Not retired Normal for live content.

The failure callout

When something has gone wrong, this panel shows a failure code with remediation text. Three codes appear here:

  • CLI_VALIDATION_STALE — validation has been running over five minutes. Press Retry validation.
  • CLI_REVIEW_REJECTED — a reviewer refused this version. A new version is required.
  • The code of the first blocking validation issue — go to the issues table and work through it. See Validation issues.

What each evidence panel proves

Panel 02 grows as the curriculum advances. Each block appears only once the corresponding thing has happened, so their presence is itself information.

Block Appears when Proves
Draft identity An import exists Which package and version this is, its opaque platform identifier, how many validation attempts have run, and whether this receipt is original or a replay.
Validation evidence Validation has completed Which contract and validator version judged the package, how many errors and warnings there were, that eleven categories were applied, and the checksum of the resulting issue set.
Review decision evidence A decision has been recorded Who decided, what they decided, which package checksum and which validation report they were looking at, whether warnings were acknowledged, and why.
Publication evidence A version has been published The version identity, who published it, the approved checksum it is bound to, the four immutability guarantees, the availability policy, and the publication event identifier.
Retirement evidence A version has been retired Who retired it and why, that no new assignments will be accepted, that existing assignments continue, and that historical content is retained.
Lifecycle audit evidence You press Inspect lifecycle history The complete ordered trail. See Audit and support.

The identifiers, and which one you want

RepoFluent shows you several identifiers that look similar and are not interchangeable. This table is the one worth remembering.

Identifier Chosen by Use it to
Package identity The author's agent Recognize the same curriculum across regenerations and versions.
Package version The author Distinguish revisions of the same curriculum. Bumping it is how you resolve a byte conflict.
Content checksum Computed from your bytes Prove that what was reviewed is what was published. Approvals and acknowledgements are bound to it.
Issue-set checksum Computed from the validation result Prove which exact set of warnings a reviewer accepted.
Platform draft identifier RepoFluent Refer to this draft internally. It is opaque on purpose: an author cannot pick it, so an author cannot collide with anything.
Published version identity RepoFluent Compare versions and assign learning. Copy it when you publish — there is no picker to look it up later.
Correlation identifier RepoFluent, per request Report a problem. This is the one to quote. It lets an operator find the exact request in their records without you having to describe or send any content.
Quote the correlation identifier, not your content

Every response RepoFluent produces carries a correlation identifier, and every failure carries a stable code alongside it. Together they are enough for support to investigate, which means you never need to send a copy of your curriculum to get help.
