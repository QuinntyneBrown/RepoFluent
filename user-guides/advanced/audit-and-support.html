Audit and support

Every action in a curriculum's life is recorded in order, permanently, with who did it and when. This page explains how to read that trail, and how to use the same identifiers to get help without handing over your content.

  • Auditor
  • Author

RF-UG-18

The auditor persona

Auditor is a genuine read-only role. An auditor can read import status and the complete lifecycle history, and can do nothing else at all — no preview, no contract model, no decisions, no publication, no assignment, no retirement, not even retrying a stalled validation.

That is the point: an auditor can verify what happened without being able to become part of what happened. Authors and administrators can read the same history; reviewers cannot.

Reading the trail

Press Inspect lifecycle history. A Lifecycle audit evidence region appears, headed Ordered lifecycle record with a badge counting the events, and above the table: the package, the version, the current state, and the package checksum.

Column Tells you
Sequence Position in the record. The sequence is gap-free — a missing number would itself be evidence, and there are none.
Lifecycle evidence What happened, in words. The vocabulary is listed below.
Actor or system Which persona did it, or that RepoFluent itself did it. Validation steps are attributed to the system, not to a person.
State The lifecycle state after the event, so you can read the state machine off the trail.
Timestamp When, in UTC.
Correlation The request that caused it. This is what ties a user action to the instance's own operational records.

The event vocabulary

A complete, healthy lifecycle produces roughly this sequence. Anything absent tells you where things stopped.

Event Meaning
Uploaded An author submitted bytes and received a receipt.
Scan completed Intake safety checks passed — media type, size, shape, no executable signatures.
Validation started A worker claimed the package.
Validation completed A versioned validation receipt was produced.
Draft imported The content was persisted as a draft, invisible to learners.
Warnings acknowledged A reviewer accepted an exact set of warnings. Absent if there were none.
Approved A reviewer bound an approval to a specific checksum.
Published An administrator created one immutable version.
Version comparison viewed Somebody compared two versions. Recorded because refresh decisions are justified by it.
Retired An administrator withdrew the version, with a reason.

Refusals are recorded too — a replayed upload, a package-version conflict, and an intake rejection all leave a trace, so a failed attempt is as visible as a successful one.

What to check when auditing

  1. Is the sequence complete?

    Upload, scan, validation, draft import, review, publication. A gap means the lifecycle stopped there, and the operational evidence panel names the failure code.

  2. Did different people approve and publish?

    Compare the actors on Approved and Published. The product does not require them to differ, so this is exactly the kind of thing an audit exists to check.

  3. Do the checksums line up?

    The checksum in the review decision evidence and the approved checksum in the publication evidence must be the same value. If they were not, publication would have been refused — confirming it is a two-second check that the binding held.

  4. Were warnings acknowledged, and why?

    If Warnings acknowledged is present, read the reviewer's rationale in the decision evidence. An acknowledgement with no explanation is worth a question.

  5. Was a retirement justified?

    The retirement reason is mandatory and permanent. Check that it names why and, ideally, what replaced it.

Preview limitation — the scope of the audit trail

What is recorded is the curriculum lifecycle. There is no access log, no record of sign-ins (there is no sign-in), no role-change history, no report exports, and no export of the trail itself — you read it on screen. Assume the trail covers content governance and nothing wider.

Getting help

RepoFluent is built so that you can report a problem precisely without sending anybody your curriculum. Two values do the work.

The correlation identifier
Attached to every response and shown in the lifecycle operations panel as the support correlation. It lets an operator find the exact request in their records.
The stable code
Every failure carries one, such as CLI_VALIDATION_STALE or CIC_REVISION_MISMATCH. Codes do not get reworded between releases, so quoting one is unambiguous. See Validation issues.

What to include in a report

  • The correlation identifier and the stable code.
  • Which persona you were and what you pressed.
  • The lifecycle state shown in the status pill, and the package identity and version — not the package itself.
  • What you expected instead.
  • Your browser, if the problem is visual or a matter of interaction.
Do not send curriculum content to get support

Source code, documentation, generated lessons, answer keys, and learner activity are all treated as customer data. The identifiers above are designed to make sharing content unnecessary, and diagnostic messages are written so as not to reproduce your content — a suspected credential, for example, is reported without ever echoing the value.
