The authoring kit

The kit is everything an agent needs to turn approved source material into a valid curriculum package, plus the tools to prove the package is valid before it leaves your environment. It runs entirely offline and needs no network access at any point.

  • Author
  • Node.js 22 or later

Verify what you downloaded

From the release directory

node scripts/verify-release.mjs

Checks every declared artifact against its recorded hash. Run this first; a kit that does not verify should not be used.

The authoring workflow

The kit's tools are meant to run in order. Each one gates the next, so a problem is found at the earliest point where it can still be cheap to fix. All of them read only the files you name.

  1. Bound the scope, before reading anything

    node scripts/preflight.mjs <scope.json>

    Resolves the repository's own policy files from the root down to each directory, applies your explicit exclusions, requires a declared repository revision and document scope, and scans the resulting file set for suspected credentials.

    Why this runs first It is deny-by-default: nothing is in scope unless it was declared. If a suspected credential is found, preflight stops — and the report gives you the path and a code but never reproduces the value, so the report itself is safe to share.
  2. Check the evidence and the uncertainty

    node scripts/validate-evidence.mjs <evidence.json> <scope.json>

    Reruns preflight, then binds every citation to a repository revision, an effective path, a file hash, and a line range. It also requires that material uncertainty stays visible in the package rather than being smoothed away.

    This is the honesty gate A conflict between sources that is not represented in the package is blocking. An agent is not permitted to pick a side silently.
  3. Verify the ecosystem analysis

    node scripts/verify-ecosystem-analysis.mjs dotnet <analysis.json>
    node scripts/verify-ecosystem-analysis.mjs angular <analysis.json>

    Each ecosystem profile defines eleven categories of evidence. Verification confirms the analysis is resolved from supplied source rather than inferred — for example, an Angular flow step with no supporting source evidence is blocking.

  4. Generate stable identifiers

    node scripts/generate-identities.mjs <identities.json>

    Identifiers are derived from semantics, not from display titles. Rewording a lesson keeps its identity, which is what makes version comparison meaningful later. A semantic-key collision is reported and blocks, rather than one entity quietly overwriting another.

  5. Validate the package

    node scripts/validate.mjs <package.json> --contract auto --format json --threshold warning

    This is the same validation RepoFluent applies, reporting the same stable codes. Options: --contract takes auto or 0.1.0; --format takes json or text; --threshold takes info, warning, or error and hides lower severities without changing whether the package is valid.

  6. Finalize the generation manifest

    node scripts/finalize-generation.mjs <run.json> <package.json>

    Produces a manifest binding the tool, model, version, source snapshot, time, package checksum, options, and validation result. The fields are allow-listed: no hidden reasoning, no credentials, and no full prompts can end up in it.

Validator exit statuses

The statuses are deterministic, which is what makes the validator safe to put in a build. Note that a warning is not a failure — it exits 3, distinctly from both success and failure, so you can decide your own policy.

Status Outcome Meaning and what to do
0 success Nothing at or above your threshold. Upload with confidence.
3 warnings-only Warnings without any blocking issue. The package will import, but a reviewer will have to acknowledge the exact warnings — so tell them what they are and why.
1 validation-failure A blocking issue. Fix it. RepoFluent would reject this package too.
2 invalid-invocation Your arguments or the package path are wrong. Nothing was validated — this is not a verdict on your content.
4 internal-failure The bundled validator could not start or finish. Re-verify the release; again, not a verdict on your content.

JSON output contains valid, outcome, contractVersion, threshold, and ordered issues. Each issue carries a stable code, a severity, whether it isBlocking, a path, and a safe message. Every code is explained on Validation issues.

Nothing has to leave your environment to be checked

Every tool here runs locally with no network access, and the kit installs no dependencies. You can hold a package to the full contract before anyone outside your approved environment ever sees it. That is the point of the kit.

The five policy panels on the page

Beneath the artifact table the page presents five reference panels. They are documentation, not controls — nothing on them is interactive — and each one states the rule its corresponding script enforces.

Scope preflight
Deny by default; repository policy resolved from root to directory; declared sources only; explicit exclusions; secret patterns stop analysis before it starts.
Evidence ledger
Claims bound to snapshots, uncertainty recorded explicitly, unrepresented material conflicts blocked.
Deterministic generation
Prose-independent identities for each entity kind, collisions stopped rather than merged, and a manifest that cannot leak private data.
Local validation matrix
Contract auto-detection, JSON or text output, severity thresholds, and the distinct exit statuses above.
Ecosystem analysis profiles
Eleven evidence categories each for C# and Angular, explicit uncertainty for dynamic registration, and a five-step trace from a user action to an API boundary.
