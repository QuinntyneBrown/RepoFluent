Comparing versions

Code changes, so curriculum goes stale. When a new version of the same curriculum is published, comparison answers the question that actually matters: does anyone who already learned the old version need to come back?

  • Reviewer
  • Administrator
RF-UG-16

What you need first

Comparison works between two published versions of the same package identity. Both must exist before you can compare, so the normal sequence is:

  1. Publish version one

    Upload, review, approve, publish. Copy the version identifier from the publication evidence.

  2. Publish version two

    The author regenerates the package against a newer source snapshot, increments the declared package version, and the whole lifecycle runs again. Copy this version identifier too.

  3. Compare, from the newer one

    Open the newer version and paste the older identifier as the base. The comparison is directional: base is where learners have been, target is where they are going.

There is no version picker

The base version has to be typed or pasted in by hand as an identifier. Nothing in the product lists published versions for you. This is the single most common reason people get stuck here, so copy version identifiers out of the publication evidence at the moment you publish and keep them somewhere. See Publishing and assigning.

Running a comparison

With a published or retired curriculum open, and as a reviewer or an administrator, find Compare published versions.

  1. Paste the base version identifier

    Into the field labelled Base published version. The submit button stays disabled while it is empty.

  2. Press Compare versions
    What you should see A Semantic version comparison section headed with the base and target versions, a refresh verdict pill, any affected objectives, and a table of changes.

When it is refused

Refusal Cause
Base version not found The identifier does not name a retained published version. Check for a copy-paste error before assuming anything worse.
Package mismatch The two versions belong to different curricula. Comparison is only meaningful within one package identity.
Distinct versions required You have given the same version twice.
No comparison form at all Your persona is not Reviewer or Administrator, or the curriculum has never been published.

Every comparison you run is recorded in the lifecycle history as Version comparison viewed. Looking is an audited action, because the comparison is what a refresh decision is justified by.

Reading the result

The comparison is semantic, not a text diff. It reports changes to meaningful entities — lessons, assessments, sources, ordering — rather than changed characters. The table has four columns.

Classification
The kind of change. The five kinds are listed below.
Stable entity
The type and identifier of the thing that changed. Because identifiers are stable across regenerations, this tells you it is the same lesson that changed rather than a new one appearing.
Impact
What the change means for a learner.
Evidence
What the judgement is based on.

The five classifications

Classification Means Usually implies
Source changed The code a lesson is built on is different — a new commit, a moved file, a changed line range. review carefully The explanation may no longer match reality.
Assessment changed A question, its options, its scoring, or its objective mapping is different. review carefully Prior results were measured against different items.
Removed An entity that existed in the base version is gone. review carefully Objectives that depended on it may now have no coverage.
Reordered The same content, in a different sequence. low concern Understanding is not invalidated by ordering.
Presentational Wording or formatting only, with no change in meaning. no concern

The refresh verdict

A pill reads either Learner refresh required or No learner refresh, and any objectives affected are listed beside it. Treat it as a well-informed recommendation, not an instruction: it is derived from the classifications, and you know things about your team that the comparison does not.

Deciding what to do

Existing learning records stay attached to the version they were earned on. Nothing you decide here rewrites history — you are deciding what happens next.

If the comparison shows A reasonable response
Only presentational and reordered changes Publish and assign the new version to new learners. Leave existing learners alone.
Source changed on a few lessons Assign the new version to the affected learners as targeted refresh work, and say in the assignment why.
Assessment changed, or objectives lost coverage Treat prior results on those objectives as no longer current. This is the case where reassignment is genuinely warranted.
Substantial removal or restructuring Retire the old version so it stops being assigned, and assign the new one broadly. See Retiring a version.
Preview limitation — refresh is a manual decision

RepoFluent does not act on the verdict. There is no mechanism to require a retake, to invalidate a prior result, to notify a learner, or to grant or withdraw credit. Comparison tells you what changed; carrying out the decision means assigning the new version and telling people yourself.
