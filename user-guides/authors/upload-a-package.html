Uploading a package

Uploading is one field and one button, but what happens afterwards is worth understanding: RepoFluent takes your file, hands you a receipt immediately, and validates it in the background. Everything that follows in the lifecycle is bound to the receipt you get here.

  • Author
RF-UG-09

What RepoFluent will accept

The field is labelled Curriculum package and its hint reads JSON · validated against schema and policy · active content is rejected. Four hard limits are checked before your file is even given a receipt.

Rule Limit
File type A single .json file, or a file sent as application/json. Nothing else.
Size 512 KiB maximum, and it must not be empty.
Content shape Strict UTF-8 JSON with a single object at the root. No comments, no trailing commas, and nesting no deeper than 128 levels.
No executables Files that begin like a Windows or Linux executable, a zip archive, or a PDF, or that contain null bytes, are refused outright.

Anything that fails these checks is rejected with a code beginning CLI_ and no receipt is created — the upload simply did not happen. Codes and remedies are listed on Validation issues.

Validate offline first

The authoring kit includes a validator that runs on your machine with no network access and reports the same codes RepoFluent will. Running it before you upload turns most of this page into something you never need. See The authoring kit.

Uploading

  1. Set your persona to Author

    Only an author can upload. As any other persona, panel 01 either refuses the action or is not offered.

  2. Choose the file

    Use the Curriculum package field in panel 01.

    What you should see The live status region changes to Curriculum package selected.
  3. Press Upload and validate

    If you press it without choosing a file first you get an inline error attached to the field reading Choose a curriculum package first. Select a JSON package, then try again. — the message is linked to the field, so a screen reader announces it with the field.

  4. Let it work

    The button becomes busy and the status region moves through Uploading curriculum package then Validating curriculum package. RepoFluent is polling on your behalf; do not press anything again.

Every message the status region can show

The region is labelled Curriculum operation status and is announced as it changes, so you can follow the whole upload without watching the screen.

Message Meaning
Ready for a curriculum package Nothing selected yet.
Curriculum package selected A file is chosen but not sent.
Uploading curriculum package The file is on its way.
Validating curriculum package Accepted; a background worker is checking it.
Curriculum package is ready for review Success. A draft exists and a reviewer can take it from here.
Existing draft reused You uploaded bytes that are already on file. See Uploading again.
Curriculum operation failed: … Something was refused. The rest of the message names what.

Reading the receipt

Panel 02 is your evidence. A status pill at the top names the current state:

Queued for validation Validating Ready for review Validation failed

Draft identity

Four fields, and the distinction between them matters.

Package identity
The stable identifier your authoring agent chose. It is the same across regenerations of the same curriculum.
Package version
The version your package declares. Together with the package identity, this is what RepoFluent uses to decide whether an upload is new, a replay, or a conflict.
Platform draft
An opaque identifier RepoFluent generated for this draft. It is deliberately separate from your identifiers so that choosing an identifier can never let you overwrite somebody else's content.
Validation attempts
How many times validation has been run for this draft.

Content checksum and correlation

The Content checksum is a sha256: value over your exact bytes. Approval, warning acknowledgement, and publication are all bound to it — change one byte and those decisions stop applying. The Correlation identifier is the value to quote when you ask for help; it ties your upload to the instance's own records without exposing your content.

Validation evidence

A versioned validation receipt recording the contract version, the validator version, a count such as 0 errors · 1 warning, the number of check categories applied (eleven), and an issue-set checksum over the exact set of issues found. If warnings exist, a warning gate appears here reading Acknowledgement required — only a reviewer can clear it.

Errors block, warnings do not

Any error at all means no draft and no path forward until you fix it and upload a new version. Warnings produce a perfectly reviewable draft, but a reviewer has to acknowledge the exact set of them before approving. Both are explained fully on Validation issues.

Uploading again

Re-uploading is safe and predictable. RepoFluent compares your package identity, your declared version, and your bytes, and does one of three things.

Situation What happens What to do
Same identity and version, identical bytes The existing receipt comes back, badged Existing receipt, and the status reads Existing draft reused. No duplicate draft is created. Nothing. This is what makes re-running an authoring pipeline harmless.
Same identity and version, different bytes Refused with CLI_PACKAGE_VERSION_CONFLICT — …already exist with different bytes. Use a new version. Increment the version in your package and upload again. This is the rule that stops content being silently swapped under a version somebody already reviewed.
Two identical uploads at once One succeeds; the other is refused with CLI_INTAKE_RETRY. Wait a moment and upload again. It is a transient collision, not a rejection of your content.

Your place is remembered

The import you are working on is remembered in your browser, so reloading the page or switching persona brings the same panel 02 back rather than losing it. Clearing site data or using a different browser starts from an empty upload panel.

When validation stalls

Validation normally finishes in a moment. If a draft sits in Validating for more than five minutes, RepoFluent treats it as stale, shows the failure code CLI_VALIDATION_STALE, and offers a Retry validation button.

  • Only an author or an administrator sees the retry button, and only while the draft is genuinely stale.
  • Retrying is safe. It re-queues the same bytes; it does not create a second draft and it does not change your checksum.
  • The attempt is recorded, so Validation attempts increases and the history shows the retry.

If retrying does not clear it, the background worker is probably not running. Quote the correlation identifier to whoever operates the instance — see Audit and support.

What you can and cannot do next

With a draft in hand, an author can inspect it but not advance it. That separation is the whole point of the workflow.

You can
Read the full import status and validation evidence, open Inspect contract model to check how RepoFluent interpreted your package, read the lifecycle history with Inspect lifecycle history, and retry stale validation.
You cannot
Acknowledge warnings, approve, reject, publish, assign, or retire. Those belong to a reviewer or an administrator. The Preview draft button is offered to reviewers only — as an author, use Inspect contract model, which is available on any draft or approved version.

Inspect contract model is the most useful of those. It shows your package back to you as RepoFluent understood it — metadata and source snapshots, the architecture model, the learning model, the assessment model with correct answers withheld, and your declared provenance, assumptions, omissions, and unresolved questions. It is the fastest way to catch a package that validated cleanly but does not say what you meant. The same workbench is described from the reviewer's side on Reviewing a draft.
